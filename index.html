Moving production observability off New Relic

I moved production logging and monitoring for our retail trading platforms from New Relic to a self-hosted stack: Filebeat, Elasticsearch and Kibana for logs and Prometheus with Grafana for metrics. Monitoring cost dropped from about $1,225 a month to $400, and I designed the retention rules that keep it there.

~$1,225 → $400monitoring cost per month
~67%lower monitoring spend
~$10Ksaved per year
~15 GBproduction logs per day

The problem

Our trading platforms run on Kubernetes, and we paid New Relic for logs and monitoring. The bill was about $1,225 a month. Production produces around 15 GB of logs a day, so keeping everything in a hosted tool was the expensive path. We needed the same visibility for a fraction of the cost, with retention we controlled.

What I did

  • Built the log pipeline: Filebeat collects container and node logs and ships them straight to Elasticsearch, which stores and indexes them, and Kibana is where the team searches and builds views.
  • Set up Prometheus to scrape cluster and service metrics, with Grafana dashboards on top.
  • Configured alerting on the metrics so the team hears about problems quickly.
  • Added Uptime Kuma to check availability of our customer-facing web platforms, with alerts when a check fails.
  • Designed index lifecycle (ILM) and snapshot lifecycle (SLM) policies so storage stays bounded as log volume grows.

Retention design

Log storage is where self-hosting gets expensive if nobody plans for it. Staging indices are deleted after 7 days. Production indices stay searchable in Elasticsearch for 30 days, then live on as snapshots until day 150, so we can restore older logs for an investigation without paying to keep them hot. Indices roll over every day or at 5 GB, which keeps each one a predictable size.

# illustrative: production log policy, shape matches the real rules
PUT _ilm/policy/prod-logs
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_age": "1d", "max_primary_shard_size": "5gb" }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": {
          "wait_for_snapshot": { "policy": "prod-snapshots" },
          "delete": {}
        }
      }
    }
  }
}

# illustrative: snapshots kept for 150 days
PUT _slm/policy/prod-snapshots
{
  "schedule": "0 30 1 * * ?",
  "name": "<prod-logs-snap-{now/d}>",
  "repository": "log-snapshots",
  "retention": { "expire_after": "150d" }
}

Result

Monitoring cost went from about $1,225 a month to $400, roughly 67% lower and about $10K saved a year. The team kept log search, dashboards and alerting, and we now control how long data is kept. I own the stack day to day: pipeline changes, dashboards, alert rules and retention.

What I'd do next

As traffic grows, I would add Elasticsearch replicas and more nodes for high availability. I would move alerting toward SLOs, so alerts fire on user-facing error budgets instead of raw thresholds. I would also look at OpenTelemetry to add traces and keep instrumentation portable as the company moves to AWS EKS.

Almost-daily releases to live trading platforms, after the market closes

Quantman is hosted for 4 major Indian stockbrokers and 2 white-label partners. Production changes ship almost every day, after Indian market hours end at 15:30 IST. I own deployments for a subset of Quantman's 13 microservices and help with the rest and with Instaoptions. I also handled 3 broker deployments of Quantman as the technical point of contact.

13Quantman microservices on a ~10-node cluster
Almost dailyproduction releases, after 15:30 IST
3broker deployments (2 end-to-end, 1 support)

The problem

Traders use these platforms while the market is open, so a bad release during or near market hours hits people with live positions. Releases have to land in the window after close and keep services available while pods are replaced. Each broker also gets its own deployment of Quantman.

What I did

  • Shipped releases through Jenkins (CI), Helm charts and ArgoCD, which syncs the cluster to what is in Git.
  • Used Kubernetes rolling updates with readiness probes, so a new pod only takes traffic once it reports ready.
  • Tuned maxSurge and maxUnavailable to keep trading services available while old pods are replaced.
  • Wrote ArgoCD Application manifests for newly deployed services, so they follow the same GitOps path as the rest.
  • Handled 3 broker deployments of Quantman: 2 end-to-end and 1 in a support role.
  • Acted as the technical point of contact for the broker's team. I gathered infra requirements, raised IP-whitelisting and network-access requests, attended networking and security meetings and handled security escalations.
# Illustrative only: generic names, not production values
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # add one new pod before removing an old one
      maxUnavailable: 0   # never drop below the desired replica count
  template:
    spec:
      containers:
        - name: api
          image: registry.example.com/api:1.4.2
          readinessProbe:      # no traffic until this passes
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3

Result

Production changes ship almost daily in the window after market close. Rolling updates with readiness probes replace pods gradually, so trading services stay available while a release goes out. New services get an ArgoCD Application manifest and follow the same Git-driven path as existing ones. I handled three broker deployments of Quantman (two end to end, one in a support role) and was the technical point of contact for the broker's team.

What I'd do next

I want to try progressive delivery with Argo Rollouts, so a release goes to a small canary first and is promoted only if its metrics look healthy. I'd pair that with automated rollback when an SLO error budget starts burning too fast. For the company's move to AWS EKS, I'd like to define the new infrastructure in Terraform from the start, which also means taking my Terraform skills past the basics.

Scoped access and audit hardening for a trading platform

Quantman runs in-house for 4 major Indian stockbrokers and 2 white-label partners, so who can touch the cluster matters. I set up namespace-scoped Kubernetes RBAC so developers can debug their own services without reaching cluster internals. I also supported VAPT and SOC audits with an external audit firm and remediated the findings.

13high-severity findings closed
Nonedeveloper access to cluster-critical namespaces

The problem

Developers need to read logs, port-forward to a service and open a shell in a pod to debug what they own. Cluster-wide access would make that easy, but it would also expose kube-system and other cluster-critical namespaces. At the same time, the company was going through VAPT and SOC audits. Auditors needed access to inspect the cluster, and we needed audit logs to show what happened inside pods.

What I did

  • Wrote namespace-scoped Roles and RoleBindings. Developers can list pods and services, port-forward and exec only in their own app namespaces.
  • Kept kube-system and kube-node-lease out of every developer binding. A request there has no matching rule, so the API server denies it.
  • Gave the external audit firm scoped cluster access for the VAPT and SOC work.
  • Set up pod-level audit logging with rsyslog so activity inside pods leaves a record.
  • Worked through the audit findings and remediated them until the 13 high-severity vulnerabilities were closed.
  • Took part in on-call, including off-hours security escalations with broker clients. One of them was a 4 AM call on a Sunday.
# Illustrative only: the shape of a developer Role, not the production manifest.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer
  namespace: team-app
rules:
  # read pods, their logs and services
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services"]
    verbs: ["get", "list", "watch"]
  # kubectl port-forward and kubectl exec need create on these subresources
  - apiGroups: [""]
    resources: ["pods/portforward", "pods/exec"]
    verbs: ["get", "create"]

Result

Developers can debug their own services without asking for admin access, and no developer binding reaches kube-system or kube-node-lease. The audit firm got the access it needed for VAPT and SOC, pods now produce audit logs through rsyslog, and 13 high-severity vulnerabilities from the findings are closed.

What I'd do next

I would move these rules into policy as code with Kyverno or OPA Gatekeeper, so a risky manifest is rejected at admission time instead of found in an audit. I would add image scanning with Trivy to the Jenkins pipeline so vulnerable images fail the build. I would also move application secrets into a dedicated secrets manager as part of the move to AWS.
